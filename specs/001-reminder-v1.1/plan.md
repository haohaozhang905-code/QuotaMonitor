# 提醒机制 V1.1 技术执行计划

## 1. 执行目标

将 `QMR-001` 的固定提醒规则落到统一规则目录、条件执行器、版本化去重账本和独立投递层，并为数据新鲜度、冷启动、迁移、权限降级和真实界面验收建立证据。

本计划根据当前实现重建，用于解释现状、补齐追踪关系，并作为后续提醒版本的技术基线。

## 2. 当前架构

```text
QuotaStore 与来源健康状态
        │ 新鲜额度、余额、重置机会、Token
        ▼
ReminderCoordinator
        │ 组装 ReminderContext
        ▼
ReminderRuleCatalog + ReminderCondition
        │ 规则排序、条件判断、事件生成
        ▼
ReminderRuleEvaluator
        │ 读写 ReminderRuleLedger V5
        ▼
ReminderCoordinator
        │ 本地化文案
        ▼
ReminderDeliveryController
        ├─ macOS 系统通知
        └─ 应用内 NSPanel 卡片
```

## 4. 技术设计

### 4.1 统一规则目录

`ReminderRuleCatalog` 是固定规则的唯一登记入口。每条规则声明：

- 稳定规则 ID；
- 依赖的数据源；
- 条件和参数；
- 去重策略；
- 固定顺序；
- 点击目标；
- 本地化文案键。

新增普通阈值时优先增加目录定义、文案和测试。只有出现新的条件语义时才扩展执行器。

额度提醒和所有可着色界面共同复用 `QuotaRiskPolicy`：显示值 31%～100% 为正常，6%～30% 为需关注，0%～5% 为高风险。重置时间不参与颜色或风险计算，避免同一百分比在不同页面或不同重置时刻改变等级。

### 4.2 新鲜度上下文

`ReminderContext` 只接收带观测时间和 `isFresh` 的数据。Coordinator 根据来源健康、路由和同轮请求对齐情况构造上下文。

约束：

- Codex 额度只在官方路由且来源可用时参与；
- 重置机会需要与当前额度属于同一轮可信请求；
- DeepSeek 余额只在对应路由生效；
- Token 需要至少一个正常来源；
- 失败结果不改写上一条有效观测。

### 4.3 条件执行器

当前条件类型：

- 多档额度阈值；
- 额度窗口变化；
- 到期时间窗；
- 带恢复线的余额阈值；
- 周期内最高里程碑。

条件执行与投递分离，避免在通知层重复业务判断。

额度窗口变化使用恢复边沿状态机：低于 100% 的新鲜观测为对应指标启用一次重置提醒；恢复至 100% 且重置时间推进后，按当前观察时间与旧窗口结束时间的关系区分按时或提前重置，并立即关闭提醒资格。连续 100% 期间的新重置时间只更新观测基线，不产生事件。重置 occurrence 绑定旧窗口结束时间，避免服务端持续调整下一次重置时间时生成不同事件。

### 4.4 去重账本与迁移

`ReminderRuleLedger` V5 按规则 ID 保存：

- 已触发 occurrence；
- 当前激活状态；
- 周期键和最高里程碑；
- 上一条 Codex 新鲜观测。
- 5 小时与周额度各自的重置提醒启用状态。
- 额度补充周期、已提醒档位、上一条显示百分比和原始重置时间。

迁移顺序为 V1 / V2 / V3 → V4 语义准备 → V5，V4 则直接迁入 V5。迁移先根据上一条显示百分比初始化重置提醒资格，再把旧 occurrence 和无窗口档位折叠为 V5 的已提醒档位。已观察到 5% 时同时视为 30% 已处理；上一条观测为 100% 时开启新的额度周期。旧键继续保留，供兼容与回滚读取。

任何新增持久语义都必须：

1. 定义稳定 ID；
2. 说明旧数据如何映射；
3. 覆盖升级后不重复和仍可继续提醒；
4. 保留可读的旧键或明确回滚限制。

### 4.5 投递层

投递层只消费已经生成并完成本地化的 Presentation：

- 已授权时投递系统通知；
- 系统渠道不可用时创建应用内 `NSPanel`；
- 卡片位置按当前屏幕 `visibleFrame` 夹紧；
- 多卡片按稳定间距排列；
- 点击、关闭、悬停和自动消失分别处理。

卡片视觉、组件状态、无障碍和浅深色验收遵循 [`docs/DESIGN_SYSTEM.md`](../../docs/DESIGN_SYSTEM.md#84-提醒卡片)。尺寸等实现值由公共设计规范与 `ReminderToastView` 保持一致，不在投递层重复建立另一套视觉语义。

状态栏身份、登录项和安装流程不属于本计划。

### 4.6 刷新唤醒与等待边界

- Token 文件系统事件使用首事件定时、后续事件合并的唤醒策略，连续写入不能无限延长等待；
- 新事件不能取消正在执行的 Token 扫描；扫描期间若再次变化，完成后只安排一次补刷；
- 5 分钟轮询继续作为文件事件丢失、休眠恢复和异常状态的兜底；
- Codex 额度与 DeepSeek 余额在同轮都需要时并行请求，提醒仍只在本轮新鲜结果提交后统一判断；
- 刷新时序不得绕过新鲜度、来源健康和完整 Token 聚合约束。

### 4.7 离席静默与 V5 去重整改（2026-09-19）

AppDelegate 持有可交互状态监测器：监听 NSWorkspace 屏幕及系统睡眠/唤醒，核对实际显示器状态；锁屏信号单独适配并在目标 macOS 真机验证。未知状态关闭真实提醒。合盖但外接屏亮且会话解锁时正常提醒。离席期间刷新展示数据，但不评估规则或积攒通知；解锁时合并触发，等待在途刷新或启动新刷新，只有本次成功的新鲜来源参与判断。

额度 30%/5% 档位按已确认的补充周期保存已提醒状态，不再以可能滑动的 resetAt 秒级值识别新一轮。观察到低于 100% → 100% 且原始重置时间推进，才发送重置提醒并开始新周期；可信越窗及明显额度恢复可重新启用低额度档位，但当前未满额时不发送“已重置”。无可靠窗口或恢复证据时保持当前已提醒状态。V4 及旧账本迁入 V5，保留旧键，避免升级后低额度重弹。

规则先产出候选状态，投递前复核可交互状态；只把实际接受投递的事件记为已提醒。异步授权等待中熄屏时丢弃候选，解锁后依据最新数据重新判断。不同类别保持独立提醒，不使用全局冷却时间。

## 5. 实施阶段

### Phase 0：建立基线

- 确认现有规则、设置和投递路径；
- 记录旧账本结构和用户可见行为；
- 确认自动测试、真实 App 和视觉验收的边界。

### Phase 1：规则与事件模型

- 建立统一规则目录和条件执行器；
- 为额度、重置、到期、余额和 Token 定义稳定事件；
- 固定事件顺序与跨档策略。

完成标准：规则目录唯一、规则 ID 唯一、顺序稳定、边界测试通过。

### Phase 2：规则 ID 账本与 V5 迁移

- 将各类去重状态迁入规则 ID 状态；
- 实现 V1～V4 到 V5 的顺序迁移；
- 保留旧键并补迁移回归测试。

完成标准：升级不重复，低额度仍可从 30% 进入 5%，重启后状态保持。

### Phase 3：数据新鲜度与 Coordinator

- 从 Store 和来源健康构造 `ReminderContext`；
- 对齐额度与重置机会批次；
- 实现用户主动重置抑制和事件合并；
- 统一中英文文案渲染。

完成标准：失败、过期和缓存数据不产生新事件。

### Phase 4：投递与设置

- 实现系统通知和应用内卡片降级；
- 接入总开关与系统授权状态；
- 实现自动消失、悬停暂停、关闭和点击跳转；
- 将窗口位置限制在可见区域。

完成标准：无通知权限仍可见；测试提醒不污染真实状态。

### Phase 5：自动化验证

- 覆盖规则目录完整性和文案键；
- 覆盖阈值、跨档、冷启动、重启和去重；
- 覆盖重置、主动重置、到期机会和同批事件；
- 覆盖账本迁移和设置授权；
- 运行本地化、安全与构建检查。

### Phase 6：真实应用验收

- 深色与浅色；
- 单卡片与多卡片；
- 系统通知允许、未请求和拒绝；
- 主屏及多屏边缘位置；
- 点击、关闭、悬停和 8 秒消失；
- 当前安装 App 的版本、签名和运行进程。

该阶段需要真实安装和系统权限，不能由普通单元测试替代。

## 6. 测试策略

| 层级 | 重点 |
| --- | --- |
| 纯规则测试 | 阈值、四舍五入、顺序、跨档、恢复线、里程碑 |
| 状态测试 | 冷启动、重启、周期变化、激活、恢复和文件事件合并唤醒 |
| 迁移测试 | V1～V4→V5、旧键保留、100% 基线保持关闭、已提醒档位兼容 |
| Coordinator 测试 | 新鲜度、同轮数据、文案和合并策略 |
| 设置测试 | 默认值、等待授权、拒绝授权 |
| 真实 App | NSPanel 位置、系统通知、交互、浅深色、多屏 |

## 7. 风险与处理

| 风险 | 处理 |
| --- | --- |
| 服务端重置时间持续漂移导致重复 | 额度档位按已确认补充周期去重，时间变化本身不重新启用 |
| 休眠后新窗口重新锚定、连续 100% 时重置时间不断后移 | 只有低于 100% → 100% 的恢复边沿才能触发；事件绑定旧窗口 |
| 旧缓存被误认为当前风险 | 只有新鲜观测参与事件生成 |
| 低额度一次跨过多个档位连续弹出 | 只展示最高命中档并标记低档已处理 |
| 连续文件写入反复重置防抖，Token 提醒延迟数分钟 | 首事件固定刷新截止点，后续事件合并但不顺延 |
| 新文件事件取消正在执行的扫描或撞上扫描状态后丢失 | 扫描期间记录一次补刷请求，本轮完成后再调度 |
| Codex 与 DeepSeek 串行请求拖慢额度或余额提醒 | 两类独立网络来源并行刷新，本轮完成后统一判断 |
| 用户主动兑换被误判为自动重置 | 使用同轮机会数量与双额度 100% 组合信号抑制 |
| 无系统通知权限导致提醒完全不可见 | 应用内卡片降级 |
| 菜单栏附近窗口坐标落到屏外 | 使用 `visibleFrame` 夹紧并增加多屏验收 |
| 改提醒时破坏状态栏身份 | 独立保护边界和静态门禁 |

## 8. 发布与回滚

- 发布前运行 `script/verify_refactor.sh`、`script/security_check.sh` 和 `script/verify_sdd_docs.sh`；
- 涉及 UI 时在当前构建或安装 App 中完成真实验收；

- 不在没有安装授权时替换用户当前应用。
